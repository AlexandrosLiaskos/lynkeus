# Research note: frame of the page

This note records, for each shared element of the page, how GIS programs offer it, which standard applies,
which existing function Lynkeus uses for it, the limits found and what could not be confirmed. Every source was
read on the date given. The notes on the description of a button, the dialog, the messages and the first frame
of a pane are in [data.md](data.md).

## Tool pane

| | |
|---|---|
| ArcGIS Pro | A tool opens in the Geoprocessing pane, with its parameters and, on a second tab, its environments. The Run button is at the bottom of the pane. After a run starts, a status banner is added to the bottom of the pane, with a progress bar that shows the percentage completed and a cancel button. When the tool completes, the banner states with an icon and a message whether it succeeded, completed with warnings or failed. The link View Details opens the same information in a detached window, with the tabs Parameters, Environments and Messages. The Back button at the top of the pane returns to the page viewed before, and the Run menu resets the parameters ([Use a geoprocessing tool](https://pro.arcgis.com/en/pro-app/latest/help/analysis/geoprocessing/basics/run-geoprocessing-tools.htm), [Help within the application](https://pro.arcgis.com/en/pro-app/latest/get-started/help-within-the-app.htm)). |
| QGIS | An algorithm opens in a dialog, not in a docked panel. The dialog has the tabs Parameters and Log and a set of buttons at the bottom; after a run the button Change Parameters shows while the Log tab is active ([The Toolbox, QGIS 3.44](https://docs.qgis.org/3.44/en/docs/user_manual/processing/toolbox.html)). The Processing Toolbox itself, which lists the algorithms, is docked at the right side of the window ([Training manual, QGIS 3.40](https://docs.qgis.org/3.40/en/docs/training_manual/processing/set_up.html)). |
| Function used | The component `ToolPane` in `web/src/shared/toolpane/`, with the form elements and the colours of the alert of the U.S. Web Design System 3.14.0. The bar of a run is the `progress` element of the browser, the details open in the `Dialog`, and a group of parameters is the `details` element of the browser. |
| Choices of Lynkeus | Lynkeus follows ArcGIS Pro: the form is in a pane, the run button at its foot, and the progress and the outcome under the button. The run button is at the right end of the foot. An inactive run button stays in the order of the keyboard, as an unfinished button of the ribbon does. The Enter key in a field runs the tool. These choices come from no source. |
| Limits | A tool pane has no Back button, no tab of environments and no Run menu, because Lynkeus has no list of tools inside the pane, no environments and no saved parameters. The outcome has no pop-up on hover; its details open only from the link. Lynkeus keeps no history of runs. |
| Tried | Chromium, through Playwright 1.65.1, on a private copy of the page with a trial tool that held every form element, in a window of 1440 by 900 pixels. The pane opened 288 pixels wide beside a map of 1152 pixels. With the pane open, the Zoom in button of the ribbon and a drag of the map worked, and the pane stayed open. A run showed "Requesting the layer (40 %)" with the bar and the Cancel link, then "The layer was added to the map." with the link View details, which opened the details in a dialog; the Escape key closed the dialog, left the pane open and returned the focus to the link. A failed run showed its sentence on the colours of an error. No error was written to the console and no request failed. |
| Not confirmed | Not tried in a browser: the Cancel link of a run and the colours of an outcome with a warning; the Escape key while the list of a select or the calendar of a date field is open inside a pane; a tool pane in windows of 1920 and 1024 pixels (it was tried at 1440 and 390). The tests cover the Cancel link and the outcome with a warning in the simulated browser. |

## Stack of panes

| | |
|---|---|
| ArcGIS Pro | The Contents and Catalog panes are docked on opposite sides of the window, or one is stacked on the other. Stacked panes have tabs at the bottom that switch from one pane to the other ([Introducing ArcGIS Pro, version 2.6](https://pro.arcgis.com/en/pro-app/2.6/get-started/introducing-arcgis-pro.htm)). The Escape key returns the keyboard focus to the map from the Contents pane, and Shift with Escape closes an active pane ([ArcGIS Pro keyboard shortcuts, version 3.0](https://pro.arcgis.com/en/pro-app/3.0/get-started/arcgis-pro-keyboard-shortcuts.htm)). |
| QGIS | Not read for the docking of panels. |
| Standard | The tabs follow the tabs pattern: an element with the role `tablist` holds elements with the role `tab`, each tab names its panel in `aria-controls`, only the selected tab is in the order of the Tab key, the left and right arrow keys move between the tabs, and Home and End, which are optional, go to the first and the last tab ([ARIA Authoring Practices Guide, Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)). The edge is a window splitter: the role `separator`, `aria-valuenow`, `aria-valuemin` and `aria-valuemax`, the arrow keys, and Home and End, which are optional ([ARIA Authoring Practices Guide, Window Splitter](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/)). |
| Function used | The components `Dock` and `DockPane` and the functions of `dock.ts`, in `web/src/shared/dock/`. `Pane` and `ToolPane` are built on `DockPane`. The edge uses pointer capture of the browser for dragging. |
| Choices of Lynkeus | The Contents pane is on the left, and the Catalog pane and every tool pane are stacked on the right. The tabs follow the order in which the panes appeared. A pane that appears comes to the front; when the front pane closes, the pane before it comes to the front. A tab is selected as soon as an arrow key reaches it. The Escape key returns the focus to the map from every pane, which ArcGIS Pro documents only for the Contents pane. When a tool pane opens, the focus moves to its title; when it closes, the focus returns to the element that opened it or, when that element has left the page, to the map. In a window narrower than 640 pixels a side covers the map. A side takes at most half of the window less 32 pixels. These choices come from no source. |
| Limits | A pane cannot be dragged to the other side, float or hide by itself. The splitter does not collapse the pane on the Enter key, which the pattern describes. In a window narrower than 640 pixels the edge is not shown, so the width cannot be changed there. |
| Tried | Chromium, through Playwright 1.65.1, 1440 by 900 pixels. After a real search of products the Catalog pane appeared in front of the open tool pane, with the tabs "Get layer" and "Catalog" in a row 29 pixels high; a third pane added a third tab. The right arrow key on a tab selected the next tab and its pane. Two presses of the left arrow key on the edge changed the width from 288 to 320 pixels; dragging the edge by 100 pixels gave 420 pixels, `aria-valuenow` read 420 and the map was 1020 pixels wide. Closing the front pane brought the pane before it to the front. Shift with Escape in a field closed the tool pane; Escape moved the focus to the map and left the pane open. In a window of 390 by 800 pixels the tool pane covered the map (390 pixels wide), the page did not scroll sideways, and the close button returned to the map. |
| Not confirmed | Not tried in a browser: a pane on the left side, because the Contents pane has no content yet; the keys Home and End on the edge and on the tabs; a stack of several panes in a window of 390 pixels; a row of tabs wider than its side. The tests cover the left side and the keys in the simulated browser, which does not lay out the page. |

## Keyboard focus

| | |
|---|---|
| Standard | Web Content Accessibility Guidelines 2.2 ([W3C Recommendation](https://www.w3.org/TR/WCAG22/)). Criterion 2.4.7 (level AA): the keyboard focus indicator is visible. Criterion 2.4.11 (AA): the focused element is not entirely hidden by content of the author. Criterion 1.4.11 (AA): what identifies a component or its state has a contrast of at least 3 to 1 with the adjacent colours. Criterion 2.4.13 (AAA): the indicator is at least as large as a perimeter 2 CSS pixels thick around the unfocused element, and has a contrast of at least 3 to 1 between the focused and the unfocused state. A solid line of 2 pixels inside the element against its outer edge is the smallest indicator that is still such a perimeter; a line further inside has to be thicker ([Understanding Focus Appearance](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)). |
| Design system | The U.S. Web Design System 3.14.0 gives every element that can take the focus an outline on `:focus`, with the settings `$theme-focus-color` (`blue-40v`), `$theme-focus-width` (`0.5`, 4 pixels), `$theme-focus-style` (`solid`) and `$theme-focus-offset` (`0`). A check box and a radio button take the outline 4 pixels outside their box (read in the Sass files of the npm package: `uswds-core/src/styles/settings/_settings-general.scss`, `uswds-elements/src/styles/_focus.scss`, `usa-checkbox`, `usa-radio`). |
| ArcGIS Pro and Office | Not read. No page that describes how these programs draw the keyboard focus was found, and the programs were not at hand. |
| Before | A line of 4 pixels in `blue-40v` (contrast 3.2 to 1 with white), on every focused field. It showed on the first field of a dialog also when a click had opened the dialog, because the browser counts the first focus of a dialog as focus from the keyboard. |
| Choices of Lynkeus | One line for the whole page: solid, 2 pixels, in the colour `primary`, set through the settings of the design system, so that every component of the design system takes it. It stands inside the edge of an element, so that a container which scrolls does not cut it. On a field it stands against the outside of the border, because the border of a field has the same lightness as the line (contrast 1.0 to 1) and a line inside would also hide the red border of a wrong value. On a filled button, a check box and a radio button it stays 4 pixels outside, as in the design system. The map takes a second, white line inside the first one, because the pictures of the map can have any colour. The line shows under `:focus-visible`, which the browser sets after a key press and on every element that takes typed text. A pane and a dialog give their first focus to their title, as the ARIA Authoring Practices Guide advises for a dialog whose content has to be read from its start ([Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)); the title shows the line only when the keyboard opened the pane or the dialog. A description of a ribbon button shows on focus only when the keyboard moved the focus. |
| Measured | The colour `primary` (rgb 0, 94, 162) has a contrast of 6.72 to 1 with white, 5.90 with the grey of the ribbon and the title bars, 5.39 with the blue of a pressed button, and 5.13 with the grey of a hovered button. With the colours of the map it has none that can be stated, which is why the map has the white line; the two lines have 6.72 to 1 with each other. |
| Limits | The line inside an element meets the size of criterion 2.4.13. On the map the criterion is not met for every picture: a pixel of medium lightness has less than 3 to 1 with both lines. A field that a click focuses shows the line, because it takes typed text; the browser decides this and the page does not change it. The button inside a date field that opens the calendar belongs to the browser, which draws its own black line around it. |
| Tried | Chromium, through Playwright 1.65.1, 1440 by 900 pixels. After a click on a ribbon button the title of the new pane had the focus and no line (`:focus-visible` false); after the Enter key on the same button the title had the line. The Tab key then went through the close button, the select, the text field, the radio buttons, the date field, the check boxes, the group names and the fields of the open group, each with a solid line of 2 pixels in rgb(0, 94, 162). The one exception was the calendar button inside the date field, which showed the line of the browser. A click on a check box showed no line. A dialog opened by a click gave the focus to its heading without a line; opened by the Enter key, with the line; the next Tab key went to the first field. After a pane that a click had opened was closed by a click, the focus was on the ribbon button, without a line and without its description. |
| Not confirmed | The page was not tried with a screen reader, in Firefox or Safari, on a touch screen, or with the forced colours of the operating system. |

## Form elements

| | |
|---|---|
| Standard | Criterion 2.5.8 of the Web Content Accessibility Guidelines 2.2 (level AA): a target for the pointer is at least 24 by 24 CSS pixels, or has that much room around it ([W3C Recommendation](https://www.w3.org/TR/WCAG22/)). |
| Design system | The form elements of the U.S. Web Design System 3.14.0, measured in Chromium before this change: text of 16 pixels, and fields and buttons 40 pixels high. |
| ArcGIS Pro and QGIS | Not read for the sizes of their form elements. |
| Function used | The classes of the design system, with the sizes that `web/src/shared/form/_form.scss` sets inside a pane and a dialog. |
| Choices of Lynkeus | Text of 13 pixels, as in the ribbon and the panes; error texts of 12 pixels; fields, selects and buttons 28 pixels high, as the tabs and the title bar of a pane; a check box and a radio button of 16 pixels in a line of 24 pixels; a button that looks like a link 24 pixels high. These numbers come from no source. |
| Measured | Chromium, 1440 by 900 pixels, in a pane 288 pixels wide: text field, select and date field 271 by 28 pixels with text of 13 pixels; run button 28 pixels high; label of a check box 24 pixels high; close button of a pane 24 by 24 pixels; name of a group 28 pixels high; the links Cancel and View details 24 pixels high. Contrast with the background: labels 17.22 to 1, hints 4.59, error text 6.98, border of a field 6.74, text of the run button 6.72 and of the inactive run button 5.79. |
| Limits | The date field is the one of the browser, which writes the date in the order of the user's language. |

## Explanation of a title

| | |
|---|---|
| ArcGIS Pro | An information button appears next to the label of each parameter of a tool in the Geoprocessing pane; hovering over it shows the information about the parameter in a ScreenTip. The Help button of the pane shows a summary of the tool when the pointer hovers over it ([Use a geoprocessing tool](https://pro.arcgis.com/en/pro-app/latest/help/analysis/geoprocessing/basics/run-geoprocessing-tools.htm), [Help within the application](https://pro.arcgis.com/en/pro-app/latest/get-started/help-within-the-app.htm)). |
| QGIS | Not read. |
| Design system | The tooltip of the U.S. Web Design System shows when the user hovers over or focuses on an element. Its guidance names it for helpful, non-critical information and brief descriptions, and advises against hiding information that is necessary for completing a task behind it ([Tooltip](https://designsystem.digital.gov/components/tooltip/)). Read in the npm package `usa-tooltip` 3.14.0: the tooltip takes the role `tooltip`, its trigger references it with `aria-describedby`, the Escape key hides it, it tries another side of its element when it would leave the window, and it appears with a transition of the opacity of 0.08 seconds, which is switched off when reduced motion is requested. |
| Standard | Tooltip pattern: the bubble has the role `tooltip`, the element that triggers it references it with `aria-describedby`, the bubble does not receive the focus, and Escape dismisses it; the pattern is marked as work in progress ([ARIA Authoring Practices Guide, Tooltip](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)). Web Content Accessibility Guidelines 2.2: criterion 1.4.13, content that appears on hover or focus can be dismissed without moving the pointer or the focus, can itself be hovered, and stays until the hover or the focus is removed ([Understanding Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)); criterion 3.3.2, labels or instructions are provided when content requires user input, for which `aria-describedby` is a sufficient technique together with a descriptive label ([Understanding Labels or Instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)); criterion 2.5.8, a target of at least 24 by 24 CSS pixels; criterion 1.4.11, a contrast of at least 3 to 1 for what identifies a component. A hidden element that `aria-describedby` references still gives its text to the description ([Accessible Name and Description Computation 1.2](https://www.w3.org/TR/accname-1.2/), step 2A). |
| Function used | The element `Info` in `web/src/shared/info/`, with the icon `info_outline` of the design system. The tooltip of the design system was not used, for the reason given in [data.md](data.md) for the description of a button: its script moves elements of the page. The bubble takes its look from `web/src/shared/tooltip/_bubble.scss`, which the description of a ribbon button also uses, so the page has one bubble. |
| Choices of Lynkeus | Every explanation that stood under a title is moved into this element, on the instruction of the user of 14 Nov 2026. This goes against the guidance of the design system for information that is needed for a task, such as the format of a coordinate. Lynkeus keeps the explanation tied to its field with `aria-describedby`, and a wrong value is still answered in a sentence that names the format. The circle is 14 pixels wide in a target of 24 pixels. The bubble shows at once when the pointer enters, without the delay of the button descriptions, because the button has no other use. A press on the button shows the bubble and leaves it until a press elsewhere, which is how a touch screen shows it. The Escape key hides the bubble and is not passed on, so a pane keeps the focus and a dialog stays open. The bubble stands under the button, starts at its left edge, keeps 8 pixels to the edges of the window, and stands above the button when it has no room under it. It is at most 256 pixels wide. The fade of 0.08 seconds follows the tooltip of the design system; the description of a ribbon button takes the same fade. These numbers, except the fade, come from no source. |
| Limits | The bubble has no pointer that joins it to its button. An explanation is not available to a user who cannot hover, focus or press the button, for example in a printed page. A statement of state, such as "No view is saved.", is not an explanation and stays under its heading. |
| Tried | Not tried in a browser. The tests run in the simulated browser, which does not lay out the page: they cover the showing and hiding by pointer, keyboard and press, the Escape key, the description of the field while the bubble is hidden, and the computation of the place from given sizes. |
| Not confirmed | Not seen in a browser: the appearance of the circle and of the bubble, the place of the button beside each kind of title, the place of the bubble at the edges of the window and inside a pane that scrolls, the fade, and its absence under reduced motion. Not tried: whether the Escape key that hides a bubble inside a dialog leaves the dialog open in every browser, a touch screen, and a screen reader. |

## Review of the frame

The elements of the frame were looked at in Chromium, through Playwright 1.65.1, in windows of 1920 by 1080, 1440
by 900, 1024 by 768 and 390 by 800 pixels, and their sizes and colours were measured. The table lists what was
found and changed. The numbers come from the measurements; the choices come from no source.

| Element | Found | Changed to |
|---|---|---|
| Description of a ribbon button | It stood directly under its button and covered the name of the group, and with it the top of a message. | It stands under the panel of the ribbon, 4 pixels below it. The clear strip between the button and the description belongs to the description, so the pointer can cross it: the description stayed while the pointer moved from the button onto it, and hid when the pointer left, as criterion 1.4.13 asks. |
| Messages | They stood over the top of the map, where the descriptions of the ribbon buttons show. In a window of 390 pixels with a pane open, they were squeezed into the 86 pixels that the pane left, and one message was 508 pixels high. Their text was 14 pixels, and they had a shadow. | They stand over the foot of the map, 36 pixels above its lower edge, above the scale and the credits of the map, so a description and a message do not meet. In a narrow window they stand over the pane that covers the map (374 pixels wide). Their text is 13 pixels. A line of 1 pixel replaces the shadow. |
| Pressed button of the ribbon | Its border (rgb 115, 179, 231) had a contrast of 2.25 to 1 with the white panel, under the 3 to 1 of criterion 1.4.11 for the sign of a state. | The border is the colour `primary`: 6.72 to 1 with the panel and 5.39 with the fill of the button. |
| Unfinished button of the ribbon | Its label (rgb 169, 174, 177) had a contrast of 2.24 to 1. The criteria exempt an inactive element, but the button can take the focus and its description is read. | The colour `disabled` of the design system (rgb 117, 117, 117): 4.61 to 1. |
| Heights of the ribbon | The line height of the labels gave heights with fractions of a pixel (a button of 72.8 pixels, a ribbon of 123.4), so the lines under the ribbon fell between pixels. | Whole pixels: a button of 72 pixels and a ribbon of 124. |
| Dialog | The modal of the design system is made for a web page: a heading of 22 pixels, a close button of 42 pixels, padding of 32 pixels and corners of 8 pixels. The search dialog was 596 pixels high. | A heading of 16 pixels, a close button of 32 pixels, padding of 16 pixels and corners of 4 pixels. The same dialog is 432 pixels high. |
| Close button of a pane | A target of 17 by 17 pixels, under the 24 pixels of criterion 2.5.8. The target was changed with the stack of panes; its icon stayed at 13 pixels. | 24 by 24 pixels, with an icon of 16 pixels. |
| Hint inside a field group | The field group kept the text size of the design system, 16 pixels, so the lines of a hint of 12 pixels stood 22 pixels apart. | The field group takes the text size of the form, and the lines of a hint stand 16 pixels apart. |
| Button that looks like a link | Inside a pane or a dialog it took the height and the padding of a filled button (28 pixels high, 12 pixels of padding at each side). | 24 pixels high, without padding, as the form styles state. |
| Scroll bars | The panel of the ribbon in a narrow window, the content of a pane and the tabs of a stack had the wide scroll bar of the browser. | The thin scroll bar of the browser (`scrollbar-width: thin`). |

Measured and left as it is: the header (32 pixels high, name of 14 pixels, 15.11 to 1), the tabs of the ribbon (28
pixels high; the selected tab 5.90 to 1), the names of the groups (11 pixels, 6.74 to 1), the labels of the
buttons (12 pixels, 17.22 to 1), the title of a pane (13 pixels, 15.11 to 1), the tabs of a stack (28 pixels high;
the selected tab 6.72 to 1), and the text of a message (15.42 to 1 on the warning colour). The page did not scroll
sideways at any of the four widths. At 390 pixels the panel of the ribbon scrolls sideways (835 pixels of buttons
in 380).

Not changed, because the folders belong to other parts: the scale of the map and its credits keep the look that
OpenLayers gives them.

## Keyboard use of the ribbon

| | |
|---|---|
| ArcGIS Pro | The Alt key or F10 enables access keys and shows KeyTips on the ribbon ([Use ArcGIS Pro with a keyboard](https://pro.arcgis.com/en/pro-app/latest/get-started/keyboard-shortcuts.htm)). On the ribbon the left and right arrow keys move from one tab to another, the down arrow key moves from a tab to the commands of that tab, and Tab or Shift+Tab moves among the commands of a tab ([Use ArcGIS Pro with a keyboard, version 3.1](https://pro.arcgis.com/en/pro-app/3.1/get-started/keyboard-shortcuts.htm)). |
| Microsoft Office | Alt or F10 selects the active tab. From there the left and right arrow keys move to another tab, Ctrl with the left or right arrow key moves to another group, Tab or Shift+Tab moves the focus to each command, and the four arrow keys move among the items of the ribbon ([Use the keyboard to work with the ribbon in Word](https://support.microsoft.com/en-au/office/use-the-keyboard-to-work-with-the-ribbon-in-word-467089f1-b4f9-4407-a80a-6a1f351fd44e)). The down arrow key moves from the list of tabs into the ribbon (the list of Microsoft for Word 2016, read in [a copy kept by Niagara College](https://its.niagaracollege.ca/wp-content/uploads/2017/06/Word-2016-for-Windows-keyboard-shortcuts.pdf)). |
| QGIS | Not read. |
| Standard | Tabs pattern: the Tab key places the focus on the active tab and then moves it to the next element outside the row of tabs; the left and right arrow keys move between the tabs and pass from the last tab to the first; Home and End are optional; a horizontal row of tabs does not listen for the down and up arrow keys, so that they can scroll the page ([ARIA Authoring Practices Guide, Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)). Toolbar pattern: the order of the Tab key has one stop for the toolbar and the left and right arrow keys move among its controls; the passage from the last control to the first, Home and End are optional; the focus may return to the control that last had it and goes otherwise to the first control that is not disabled; a toolbar is advised for three or more controls ([Toolbar](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/)). A disabled control that has to stay discoverable takes `aria-disabled="true"` and stays focusable, as the Copy, Cut and Paste buttons of a toolbar do ([Developing a Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)). |
| Function used | The component `Ribbon` and the functions of `keys.ts`, in `web/src/ribbon/`. The focus moves with the functions `focus()` and `scrollIntoView()` of the browser. |
| Choices of Lynkeus | The Tab key stops once on the row of tabs and once on the buttons, as the two patterns say, and not on every command as in Office and in ArcGIS Pro. Those programs enter the ribbon with Alt or F10 and leave it with the same key, while on a web page the Tab key also has to pass the ribbon to reach the map: the Map tab has 23 buttons and the Analysis tab 16. On a tab, the left and right arrow keys, Home and End select a tab as soon as they reach it, as before, and the down arrow key moves to the buttons, as in both programs. This key departs from the Tabs pattern; the page does not scroll, so the key has no other use there. On a button, the left and right arrow keys move through the buttons of all the groups and pass from the last button to the first, Home and End go to the first and the last button, and Ctrl with an arrow key goes to the first button of the group beside; Office names this key and does not state which button of the group takes the focus. The up arrow key returns from a button to the selected tab; it mirrors the down arrow key and no page read names it. The Tab key returns to the button that last had the focus, otherwise it stops on the first finished button, otherwise on the first button. A grey button carries `aria-disabled` and stays in the reach of the arrow keys, so that its description can be read. |
| Limits | Alt and F10 do not move the focus to the ribbon, and the ribbon has no KeyTips. Chromium does not scroll a button that is partly in view when the button takes the focus: at a width of 390 pixels a focused button stood 7 pixels beyond the edge of the panel. The ribbon therefore brings a button into view itself before an arrow key moves the focus to it; when the Tab key moves the focus, this is left to the browser. |
| Tried | Chromium, through Playwright 1.65.1, on the page built from this function on the commit 22167b4 of `main`, in windows of 1440 by 900 and of 390 by 844 pixels, with the same order of focus in both. From the top of the page the Tab key stopped on the map, on the link of the map credits, once outside the page, on the tab Map, on one button and again on the map; before the change the first 8 presses from the tab went through the tab Map and seven buttons in turn. On the tabs: right arrow to Data, End to Help, Home to Map, left arrow to Help, right arrow to Map. The down arrow key went to Full extent and showed its description. Three presses of the right arrow key reached Zoom to layer, a grey button, which showed "Shows the whole of the selected layer. Not yet available." Ctrl with the right arrow key went to Blue Marble and then to Rectangle, and with the left arrow key back to Blue Marble. End went to Swipe, the right arrow key from there to Full extent, and the left arrow key back to Swipe. The Escape key hid the description and left the focus on the button. The up arrow key returned to the tab Map, the Tab key from there to Swipe, the last button that had the focus, and the next Tab key to the map. The Enter key on Zoom in changed the scale bar from 2000 km to 1000 km. At 390 pixels every button that an arrow key reached stood wholly inside the panel (between 5 and 385 pixels), and the panel had scrolled by 449 pixels at the last button. No error was written to the console and no request failed. The Map tab had 12 buttons on that commit, 7 of them grey, and every one was reached. On that commit a description stood directly under its button. |
| Not confirmed | The page was not tried in a browser after this function was joined with the later commits of `main` (69f0eca at the last merge). Since the trial a description shows on focus only under `:focus-visible` and stands under the panel of the ribbon, the focus line changed, and the Map tab grew from 12 to 23 buttons. That the description still shows, and shows under the panel, when an arrow key moves the focus, and the look of the focus line on the tabs and the buttons, rest on the tests of the simulated browser alone. Not tried: a screen reader, Firefox, Safari, a touch screen, and whether Ctrl with an arrow key reaches the page on macOS. The pages of Microsoft and of Esri were read as the extracts that the web search returned, not in full. |

## Collapsed ribbon

The page Show or hide the ribbon in Office, in an earlier text, adds an arrow at the top right that minimizes the ribbon and shows it again, and describes the minimized ribbon: a click on a tab shows it, and after a click on a command it goes back to being minimized ([Show or hide the ribbon in Office](https://support.office.com/en-us/article/show-or-hide-the-ribbon-in-office-d946b26e-0c8c-402d-a0f7-c6efa296b527)). | Standard | The role `tab` supports the state `aria-expanded` ([WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)). A button that stays switched on is a toggle button: it carries `aria-pressed`, and its label does not change with its state ([ARIA Authoring Practices Guide, Button](https://www.w3.org/WAI/ARIA/apg/patterns/button/)). |
| Function used | The component `Ribbon` in `web/src/ribbon/`, the icon `expand_less` of the U.S. Web Design System 3.14.0 and the component `Tooltip` for the description of the new button. The ribbon carries the attribute `data-tooltip-row`, which `Tooltip` offers, so that this description shows under the whole ribbon, as the descriptions of the other buttons show under the panel. By its code, the `Map` of OpenLayers 10.11.0 watches its element with a `ResizeObserver` of the browser and calls its own `updateSize()` (read in `ol/Map.js` of the npm package), so the map should take the freed height by itself; this was not observed. |
| Choices of Lynkeus | Three ways collapse the ribbon and expand it again: a double click on any tab, Ctrl+F1 from any part of the page except an open dialog, and a button at the right end of the row of tabs, which also serves the keyboard alone and a touch screen. The button is named Collapse the ribbon, as the command of Office, and stays pressed (`aria-pressed`) while the ribbon is collapsed, as the other buttons of the ribbon that stay switched on, with the same fill and the same border in the colour `primary`. The selected tab states in `aria-expanded` whether its groups show. On a collapsed ribbon a click on a tab, the Enter key or the Space key on it, or the down arrow key shows the groups of the tab over the map, which keeps its size; the Ribbon control of Microsoft likewise puts them in a drop-down. The groups hide again after a finished button has run, on a second click on the same tab, on the Escape key, and when the pointer presses or the focus reaches another part of the page. The Escape key and the down arrow key are choices of Lynkeus; no page read names them for a minimized ribbon. When the groups hide while one of their buttons has the focus, the focus goes to the selected tab, and a pane or a dialog that the button opened returns the focus to that tab. A collapsed ribbon holds no buttons, so that none of them can take the focus. The button stands after the groups in the order of the Tab key, so that the Tab key still passes from a tab to its buttons, as the Tabs pattern says. |
| Limits | The ribbon starts expanded on every visit; the choice is not kept. While a collapsed ribbon shows its groups, the description of the new button is placed under the row of tabs and so stands over the right end of those groups. There is no menu on a right click and no mode that hides the tabs as well. A grey button runs nothing, so the groups that a collapsed ribbon shows stay after a click on it. The new button stands over the right end of the row of tabs: the tabs end at 339 pixels, as measured for the keyboard use, and by its style the button takes about 32 pixels from the right edge, so it would cover the end of the tab Help in a window narrower than about 371 pixels. This number is computed and was not measured. |
| Tried | Not tried in a browser. In the tests, with happy-dom 21.0.4, which does not lay out the page: a double click on a tab removes the groups, sets `aria-expanded` of the tab to `false` and leaves both tabs, and a double click on the other tab shows its groups; Ctrl+F1 does the same from a button outside the ribbon, F1 alone does nothing, and Ctrl+F1 inside a dialog does nothing; the Enter key and the Space key on the button Collapse the ribbon switch `aria-pressed`; on a collapsed ribbon a click on a tab shows its groups, a click on a grey button leaves them, a click on a finished button runs it once, removes the groups and moves the focus to the tab; a second click on the tab, the Escape key, a press of the pointer outside the ribbon and the Tab key that leaves the ribbon remove the groups, and a press of the pointer inside the ribbon leaves them; the down arrow key on a tab of a collapsed ribbon shows the groups and moves the focus to the first button; the description of a button of those groups takes its place from the panel, and the description of the new button from the ribbon. |
